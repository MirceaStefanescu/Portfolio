Build the review around a real decision

A useful evaluation starts with the behavior your product needs. The initial scope might be one structured-output task, a tool-call format or a set of prompt regression cases.

  1. Choose representative examples. Include normal cases, known failures and relevant edge cases. Remove personal or confidential data unless its use is separately authorized.
  2. State the expectation. Specify required fields, reference outputs or expected tool-call structure. Missing reference data should stay unscored instead of becoming a false pass.
  3. Separate contracts from quality. A fixture can check parsing and transport reliably; it cannot establish how a real model behaves on your actual task.
  4. Make changes reviewable. Keep prompt and dataset versions with the report, expose failed cases and choose any acceptance threshold for the specific project.

What a bounded review includes

Review of one prompt or evaluation workflow, test-case recommendations, reproducible checks where feasible and a written implementation plan. Any real-provider evaluation needs an authorized account, a representative dataset and agreed costs; none is assumed in the diagnostic.

Useful inputs are the workflow's purpose, non-sensitive examples, expected outputs and relevant code or configuration. The enquiry can start with a description; do not include API keys.
